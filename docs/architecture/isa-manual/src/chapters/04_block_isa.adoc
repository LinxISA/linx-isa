[[blockisa]]
== Block-structured control flow (Block Split)

[[blockisa-overview]]
=== Overview

Linx uses an explicit *block split* convention for control flow. Control-flow is defined at **basic-block**
granularity.

**Safety rule:** every architectural control-flow target (direct, conditional, indirect, call/return) MUST point at a
**block start marker**. Branching to an address that does not begin with a block start marker MUST raise an exception.
This rule is a control-flow integrity requirement. (Evidence: MAN-02)

* `BSTOP` terminates a block.
* `BSTART.*` / `C.BSTART.*` terminate the current block and begin the next one. (Evidence: MAN-01)
* A block may also be *implicitly* terminated by the next `BSTART.*` marker in the instruction stream (toolchain
  convention; some code emits an explicit `BSTOP`/`C.BSTOP` for clarity).
* An empty block is legal (header and boundary markers only, no payload instructions).
+
+NOTE: `BSTART.*` / `BSTOP` are treated as **block boundary markers** for block init/commit. They may appear as markers/descriptors in the program stream, but there must be no architectural state-modifying *payload* instructions outside block execution.
* Canonical v0.58 assembly uses the named `BSTART.<operation>` forms defined
  by the golden catalog. Retired block-start spellings are illegal input.
* Conditional transitions use a two-step sequence:
  1. Set the block condition using `SETC.*` / `C.SETC.*`
  2. Select the next block using `BSTART.* COND, <target>`

NOTE: `FENTRY`, `FEXIT`, and `FRET.*` template blocks are also block start markers and MUST be treated as valid control-flow targets. (Evidence: MAN-03, MAN-04)

[[blockisa-forms]]
=== Block forms (coupled / decoupled / template)

The v0.58 profile (preserving inherited v0.58 encodings) defines **three
block forms**. Toolchains and implementations MUST enforce the legality
rules in this section.

[[blockisa-forms-coupled]]
==== Coupled blocks (default scalar CFG)

Coupled blocks are the default form used for scalar control-flow graphs.

Form:

* `BSTART{.<type>}  inst*  (BSTOP | next BSTART)`

Rules:

* A coupled block begins at a block start marker and ends at `BSTOP`/`C.BSTOP` or implicitly at the next block start
  marker.
* `B.*` header descriptors MAY appear immediately after the block start marker. In coupled blocks, such descriptors
  serve as tooling metadata and MAY be treated as no-ops by scalar-only implementations unless specified
  otherwise by the platform profile.

[[blockisa-forms-decoupled]]
==== Decoupled blocks (header + out-of-line body)

Decoupled blocks split a block into:

* a **header** in the linear instruction stream, and
* a **body** located out-of-line and referenced by the header.

This form is intended for accelerator/tile execution where the block header packages execution metadata while the
actual instruction body is placed elsewhere.

*Header form (required structure):*

* A decoupled header begins with `BSTART.<type>`.
* After `BSTART.<type>`, the header stream MUST contain **only** `B.*` header descriptors (no non-`B.*`
  instructions).
* The header MUST provide exactly one `B.TEXT <label>` descriptor which defines `BodyTPC` (legacy naming for the body entrypoint).
  - Normative: `BodyTPC` is the initial **Temporary PC** (`TPC`) value used for body execution.
  - Alignment: `BodyTPC` MUST be 2-byte aligned. Misalignment MUST raise `E_BLOCK(EC_BFETCH)` with `TRAPARG0` set to the misaligned body-fetch address; this fault is **fatal** (non-restartable), see System/Privilege trap semantics.
* The header ends at `BSTOP`/`C.BSTOP` or implicitly at the next block start marker in the linear stream.

*Body form (required structure):*

* The body begins at `BodyTPC` (from the header's `B.TEXT`).
* For block types other than canonical shader kernels (`BSTART.MPAR` / `BSTART.MSEQ`), the body MUST be a **linear**
  snippet unless that block type defines a different contract.
* Generic linear bodies MUST NOT contain:
** any `BSTART.*` / `C.BSTART.*` / `HL.BSTART.*`,
** any template block (`FENTRY`/`FEXIT`/`FRET.*`/`MCOPY`/`MSET`),
** any branch/jump/call/return instruction, or any instruction that performs an architectural control transfer,
** any `B.*` header descriptor.
* A generic linear body MUST terminate at `BSTOP`/`C.BSTOP`. A body containing only `BSTOP`/`C.BSTOP` is a valid
  empty body.
* For `BSTART.MPAR` / `BSTART.MSEQ`, the body is instead a **structured instruction stream**:
** branches, jumps, and other in-body architectural control transfers are legal and execute at group granularity through
   the architectural group PC plus the current EXEC mask,
** valid terminators are `BSTOP`, `C.BSTOP`, `BSTART.*`, `C.BSTART.*`, and `HL.BSTART.*`,
** a terminator completes the current body execution only when control reaches it,
** an earlier lexical terminator does not by itself truncate the body if in-body control flow branches to a later label
   within the same `B.TEXT` body,
** `p` is the architectural 64-bit EXEC mask for the body, and `V.CMP.* ->p` is the normative mask-generation rule,
** the unified `lx64` any-operand rule applies: if any operand names `vt`/`vu`/`vm`/`vn`, the instruction executes as
   `v.*`; otherwise it executes as `l.*`,
** canonical kernel global-memory access uses bridged forms only: `l.*.brg` and `v.*.brg`.

*Header→body→return execution:*

* When a decoupled header is executed, the engine MUST execute the body at `BodyTPC` before beginning the next block
  at the header continuation address.
* On body termination, execution resumes at the header continuation address:
** if the header ended with `BSTOP`/`C.BSTOP`: continuation is the instruction address immediately after that stop,
** if the header ended implicitly: continuation is the address of the next block start marker in the linear stream.
* For `MPAR`/`MSEQ`, reaching a legal body terminator along the taken in-body control-flow path is the kernel completion
  event that returns to the header continuation point.

*Safety rule interaction (`B.TEXT`):*

* `BodyTPC` is an **engine-internal entrypoint** and need not begin with a block start marker.
* Any *architectural* control-flow transfer to `BodyTPC` (direct/cond/ind/call/ret) is illegal and MUST raise a
  dedicated control-flow-integrity exception (`E_BLOCK(EC_CFI)`) identical to branching to the interior of a coupled block.
  (Cause encoding: `EC_CFI=0x1` in `E_BLOCK`, with `EC_CFI_KIND` in `TRAPNO.CAUSE[3:0]`; see System/Privilege trap reporting.
  Precision: `E_BLOCK(EC_CFI)` is **precise** — no architectural state changes from the offending control-flow instruction are
  committed. Targets that are invalid encodings but are not *interior-entry* CFI violations remain `E_INST(EC_ILLEGAL)` unless
  otherwise specified.)
* In-body control-flow targets that escape the fetchable kernel/body region MUST fault as `E_BLOCK(EC_BFETCH)` rather
  than as an external CFI violation.

[[blockisa-forms-template]]
==== Template blocks (standalone blocks)

Template blocks are standalone blocks that execute via a *code-template generator* (see <<templates>>). They are not
wrapped by `BSTART..BSTOP`.

Commit point (template blocks): a template block commits when the template engine reports completion and control
transfers to the next block start marker (the completion boundary).

NOTE: Trap/replay for template execution uses `BSTATE.Template` (including `TemplateKind`) and the trap snapshot rules in
<<system-bstate-ebstate>> / <<system-trap-routing>>.

Rules:

* Template blocks MUST NOT appear inside `BSTART..BSTOP` coupled blocks or inside decoupled bodies.
* Template blocks MAY be targeted by architectural control flow (they are block start markers for the safety rule).

[[blockisa-exec-model]]
=== Execution model (block boundaries)

The intended execution model is block-granular:

* Instructions within a block may be implemented with out-of-order execution/commit as a microarchitectural choice.
* Block-to-block behavior is architecturally sequential: the next block begins only after the current block is
  complete.
* Implementations that issue blocks out-of-order must retire in-order with a block reorder buffer (`BROB`) and commit
  at block boundaries.
* A block may be interpreted as a variable length macro-instruction composed from 16/32/48/64-bit encodings.

This model is the motivation for explicit block delimiters and for block-local temporaries (ClockHands) whose lifetime
is bounded by the block.

[[blockisa-barg]]
=== Block Argument Register (BARG)

Blocks carry per-block architectural state called the **Block Argument Register** (**BARG**). BARG is evaluated and
committed at **block boundaries**.

In the bring-up model, BARG includes (non-exhaustive):

* the block type (e.g. `.STD`, `.SYS`, `.FP`, …),
* the selected branch/exit kind (e.g. `FALL`, `DIRECT`, `COND`, `CALL`, `IND`, `ICALL`, `RET`),
* the current predicate/condition state, and
* the selected next target (PC-relative target, or a register-based target for `RET`/`IND`-class exits).

Additional bring-up fields used by tooling and trap recovery include:

* block addresses (`BPC` / `BPCN`),
* ordering/atomic qualifiers (`AQ`/`RL` from `B.CATR` only), and
* output register mapping for split blocks.

**BARG lifetime rules (bring-up):**

* BARG is reset/initialized at block start (a block start marker).
* `SETC.*` / `C.SETC.*` update BARG and MUST execute *inside a block* (after a block start marker). `SETC` may appear
  anywhere in the block; it need not be the last instruction.
* At block commit (`BSTOP` or the next block start marker), the execution engine consults BARG and commits:
** block-to-block control flow, and
** any architectural outputs described by the block header (e.g. split-block output mapping).
* Context switches MUST preserve BARG as part of the LXCPU architectural state.

[[blockisa-block-types]]
=== Block types and branch types

`BSTART` forms encode two orthogonal concepts:

* a **block type** (e.g. `.STD`, `.SYS`, `.FP`, `.MPAR`, …), and
* a **branch type** / transition kind (e.g. `FALL`, `DIRECT`, `COND`, `CALL`, `IND`, `ICALL`, `RET`).

The bring-up profile constrains certain combinations (examples):

* `.SYS` blocks fall through only (`FALL`), optionally with a fixup label.
* `.MPAR` / `.MSEQ` are the canonical v0.58 shader-kernel launch forms and select memory-parallel versus
  memory-sequential execution modes.
* `.FP` blocks mirror `.STD` transitions but mark a floating-point execution context.

Block types beyond the scalar core use named TLSU and CUBE direct forms plus VEC/SFU aliases over the unchanged TEPL
Mode/Function carrier.
Selector space not explicitly assigned by the PTO ISA 0.58.0 catalog is reserved and must not acquire ad hoc semantics.

[[blockisa-tile]]
=== Tile blocks (TAU)

Linx defines *tile blocks* for hardware-accelerated tile operations. A tile block is a basic block that:

* starts with a tile/vector header (for example `BSTART.TLOAD`, `BSTART.TMATMUL`, `BSTART.VEC`, `BSTART.SFU`,
  `BSTART.MPAR`, `BSTART.MSEQ`, `BSTART.VPAR`, or `BSTART.VSEQ`), and
* ends at `BSTOP` / `C.BSTOP` or the next block start marker.

Tile blocks operate on **tile registers** (see <<progmodel-tile>>), and use explicit per-block descriptors:

* `B.IOT` describes tile inputs/outputs (including relative tile references and transfer sizing)
* `B.IOR` describes GPR inputs/outputs for the block
* `B.DATR` carries operation-applicable datatype, rounding, saturation, layout, comparison, and pad/byte controls
* `B.DIM` / `C.B.DIM*` may be used to provide block-local dimensions and valid masks via `LB0..LB2`

Bring-up contract (v0.58 current profile):

* Typed operation starts are canonical for TLSU and CUBE. VEC/SFU operations use
  `BSTART.VEC TileOp, DataType` or `BSTART.SFU TileOp, DataType` over the TEPL carrier.
  The raw compatibility spelling remains `BSTART.TEPL Mode, Function, DataType`.
* Retired PAR-style block-start spellings are illegal and MUST be rejected.
* `TLOAD`/`TSTORE` are the canonical memory-tile baseline for AI and rendering bring-up.
* `TMOV` is the canonical tile-state move baseline operation in the TLSU family.
* PTO VEC/SFU operations (`TADD`, `TSUB`, `TROWMAX`, etc.) use the engine alias selected by the operation catalog.
* `TVEC` is not a standalone v0.58 header mnemonic; TVEC-style execution is represented by `BSTART.VPAR`/`BSTART.VSEQ`.
* Historical `MCALL` terminology is represented by `.MPAR`/`.MSEQ` execution modes in the live profile.
* `TPREFETCH` is TLSU Function 3 and has the same architectural memory
  footprint as `TLOAD`, with all destination effects removed.

**Immutability rule (design intent):** a tile block consumes input tiles and produces a new destination tile; it does
not mutate the input tiles in-place.

NOTE: In the strict profile contract, `B.IOT` prints transfer size in KiB (for example `->t<1KB>`)
and uses `last` to mark the terminal descriptor in a block header chain. Descriptor metadata may be carried by multiple
`B.IOT` entries when the operation schema needs more tile operands. PTO direct operations accept at most one `B.IOR`;
Linx-only vector-body scalar imports may use repeated B.IOR descriptors in header order.

Inherited v0.58 descriptor rules (normative in v0.58 unless explicitly
extended below):

* `B.IOT` *tile references* are printed as `t#k` / `u#k` / `m#k` / `n#k` where `k` is 1-based.
  The encoded tile-id mapping is:
** `t#k` → tile-id `k-1` (0..7)
** `u#k` → tile-id `8+(k-1)` (8..15)
** `m#k` → tile-id `16+(k-1)` (16..23)
** `n#k` → tile-id `24+(k-1)` (24..31)
  These tile-ids name positions within the corresponding hand’s architectural tile-register queue.
* `B.IOT` and `B.IOS` TSize codes 1 through 7 map to 128 B through 8 KiB. Every other destination size code is illegal.
* A runtime-resolved size must equal one of those accepted footprints. Compiler/runtime MUST fail fast otherwise.
* `S0V` / `S1V` semantics are *inverted*: `0` means the corresponding `SrcTile*` is present as an input; `1` means absent.
  When a source is absent, its corresponding `SrcTile*` field is ignored and SHOULD be encoded as `0` in canonical v0.58 output.
* `DstTile` encodes the destination *kind* and controls where the tile-producing engine allocates the output:
** `0`: `t` hand (T queue)
** `1`: `u` hand (U queue)
** `2`: `m` hand (M queue)
** `3`: `n` hand (N queue)
** `4..6`: reserved
** `7`: illegal
  CUBE destinations use this explicit destination binding like other tile-producing operations; there is no implicit ACC singleton.
* For destination kinds `t/u/m/n`, the destination tile register is allocated implicitly as a **queue push**:
** the output becomes the new `hand#1` definition (for example `->u<4KB>` allocates a new `u#1`),
** existing definitions in that hand shift down (`hand#1→hand#2`, `hand#2→hand#3`, …),
** allocation that would exceed the architectural queue/capacity limit raises a precise fault; there is no eviction or spill.
** for `B.IOT`, the `SizeCode` updates the newly allocated (`hand#1`) tile register’s tracked byte-size.
* Input tile references (`t#k`/`u#k`/`m#k`/`n#k`) name a position in the corresponding **tile register queue**, where `k=1`
  is the most recent definition and larger `k` values refer to older definitions.
* `.reuse=0` releases an input only after successful consumer commit; `.reuse=1` retains it. Fault, retry, and squash preserve it.
* Each `B.IOR` descriptor carries up to three source GPR bindings plus one destination GPR binding.
* In the Linx-only vector-body interface, canonical shader-kernel scalar imports are the ordered namespace `ri0..ri11`:
** bindings are allocated from repeated `B.IOR` descriptors in header order,
** within one descriptor, imports are assigned in `RegSrc0`, `RegSrc1`, `RegSrc2` order.
* Each `B.IOT` descriptor carries up to two source-tile references plus one destination tile kind; repeated descriptors
  carry the complete ordered operand list when an operation needs more bindings.
* CUBE operand roles follow `isa/v0.58/state/pto_ops.json`. Every form binds `destination0`; `.ACC` forms additionally
  bind `source0` as the accumulator, followed by their matrix/vector inputs.
* `group=0` means the header descriptor chain continues.
* `group=1` is the terminal descriptor form in bring-up streams and is rendered as `last` in disassembly.
* Archived raw material that relies on other `group` values is not part of canonical v0.58 and remains reserved/illegal.
* `B.IOR` disassembly omits zero GPR inputs/outputs and prints the input list in encoding order (`RegSrc0`, `RegSrc1`, `RegSrc2`)
  (for example, `[s0,a6],[]`).

v0.58 tile header encoding families:

* TLSU-family typed forms: `31..27=DataType`, `26..25=00`, `24..20=Function`, `19..15=00010`, `14..0` fixed block-split tail.
* CUBE-family typed forms: `31..27=DataType`, `26..25=00`, `24..20=Function`, `19..15=00110`, `14..0` fixed block-split tail.
* VEC/SFU TEPL-carrier form: `31..27=DataType`, `26..25=Mode`, `24..20=Function`, `19..0` fixed block-split tail.
* `BSTART.VPAR`: `26..25=Mode`, `19..15=00100` with fixed block-split tail.
* `BSTART.VSEQ`: `26..25=Mode`, `19..15=00101` with fixed block-split tail.

v0.58 tile `DataType` field assignments (u5, inherited unchanged):

* Floating: `FP64=0`, `FP32=1`, `TF32=2`, `HF32=3`, `FP16=4`, `BF16=5`,
  `HiF8=6`, `E4M3=7`, `E5M2=8`, `E3M2=9`, `E2M3=10`,
  `E2M1X2=11`, `E1M2X2=12`, `E8M0=13`, and `HiF4X2=14`.
* Signed integer: `S64=16`, `S32=17`, `S16=18`, `S8=19`, `S4X2=20`.
* Unsigned integer: `U64=24`, `U32=25`, `U16=26`, `U8=27`, `U4X2=28`.
* Codes 15, 21-23, and 29-30 are reserved. Code 31 is illegal.

v0.58 named-form policy (normative):

* TLSU, CUBE, and TEPL name binary encoding families. TLSU and CUBE have no generic
  legal assembly form; each allocated function has an exact `BSTART.<operation>` form.
  The TEPL carrier accepts `BSTART.VEC TileOp, DataType`, `BSTART.SFU TileOp, DataType`,
  and the raw compatibility spelling `BSTART.TEPL Mode, Function, DataType`; canonical
  output selects VEC or SFU from the locked catalog.
* Named mnemonics are explicit v0.58 instruction forms in the golden catalog
  and resolve to encoding selectors:
** `BSTART.TLOAD` -> TLSU `Function=0`
** `BSTART.TSTORE` -> TLSU `Function=1`
** `BSTART.TMOV` -> TLSU `Function=2`
** `BSTART.TPREFETCH` -> TLSU `Function=3`
** `BSTART.MGATHER` -> TLSU `Function=4`
** `BSTART.MSCATTER` -> TLSU `Function=5`
** `BSTART.MGATHER.MASK` -> TLSU `Function=6`
** `BSTART.MSCATTER.MASK` -> TLSU `Function=7`
** `BSTART.MGATHER.CAS` -> TLSU `Function=8`
** `BSTART.TMOV` Shared modes -> TLSU `Function=9..12`
** `BSTART.GMOV` -> TLSU `Function=13`
** `BSTART.TSTORE` Shared partition mode -> TLSU `Function=14`
** `BSTART.TMATMUL` -> CUBE `Function=0`
** `BSTART.TMATMUL.ACC` -> CUBE `Function=2`
** VEC operations such as `TADD`/`TSUB` -> `BSTART.VEC TileOp, DataType`
** SFU operations such as `TROWMAX` -> `BSTART.SFU TileOp, DataType`
* TLSU `Function=15..31` encodings are reserved and MUST raise an
  illegal-instruction exception. They are not instruction forms and MUST NOT
  contribute to legal-form or executable-coverage denominators.
* Generic or mixed TLSU textual forms and retired tile names are illegal input.

v0.58 TLSU `Function` assignments:

* `Function=0` => `TLOAD`
* `Function=1` => `TSTORE`
* `Function=2` => `TMOV`
* `Function=3` => `TPREFETCH`
* `Function=4` => `MGATHER`
* `Function=5` => `MSCATTER`
* `Function=6` => `MGATHER.MASK`.
* `Function=7` => `MSCATTER.MASK`.
* `Function=8` => `MGATHER.CAS`.
* `Function=9..12` => Shared `TMOV` insert/publish/broadcast/extract modes.
* `Function=13` => `GMOV`.
* `Function=14` => Shared partition `TSTORE`.
* `Function=15..31` are reserved and MUST NOT appear in canonical outputs.

v0.58 CUBE named `Function` assignments:

* `0/1/2` => `TMATMUL` / `TMATMUL.BIAS` / `TMATMUL.ACC`
* `4/5/6` => `TMATMULMX` / `TMATMULMX.BIAS` / `TMATMULMX.ACC`
* `16/17/18` => `TGEMV` / `TGEMV.BIAS` / `TGEMV.ACC`
* `20/21/22` => `TGEMVMX` / `TGEMVMX.BIAS` / `TGEMVMX.ACC`
* Other 5-bit CUBE values are reserved and raise an illegal-instruction exception.

v0.58 VEC/SFU TEPL-carrier allocation policy:

* The authoritative machine-readable selector map is
  `isa/v0.58/state/pto_encoding_map.json`.
* The raw header carries `Mode[1:0]` and `Function[4:0]`.
* The canonical logical selector is `(Mode << 5) | Function`.
* The catalog assigns exactly 87 unique selectors across Modes 0 through 3;
  the remaining 41 selector positions are reserved and illegal.
* Canonical names include `TTRANS`; `TTRANSPOSE` and `TSORT32` are
  migration-only source aliases and never decode as instruction identities.
* Tile-scalar extension ops require `B.IOR` scalar RHS binding as defined by the op profile.
  - NOTE (toolchain convention): when a VEC/SFU operation requires scalar RHS data, place the binding in the first `B.IOR` entry
    where practical, even though implementations must accept any `B.IOR` position defined by the op profile.

Unassigned TEPL-carrier mode/function pairs are reserved/illegal in canonical v0.58.
Canonical toolchains MUST reject them and implementations MUST NOT assign ad
hoc semantics.

v0.58 `TMOV` contracts:

* `TMOV` is a tile-state operation; it MUST NOT directly access GM memory.
* For `DstTile` kinds `t/u/m/n`, destination allocation is queue-push only (new `hand#1`).
* Explicit destination depth encoding (`->t#k`/`->u#k`/`->m#k`/`->n#k`) is not part of v0.58.
* `B.IOT` and `B.IOS` size codes 1 through 7 select 128 B through 8 KiB; code 0 is illegal for a participating PE.
* The selected capacity applies independently to each participating PE. Allocated rows and columns are powers of two,
  rows are derived from capacity, columns, and datatype, and the valid region must fit inside that allocation.
* Layout conversion is selected only by an operation-applicable `B.DATR.Layout` value and is capability gated.

v0.58 TLSU assignments:

* The v0.58 catalog is authoritative. Unassigned TLSU functions are illegal.
* The TLSU `Function` field keeps the same header layout and grows only by assigned slots:
** `Function=3` => `TPREFETCH`
** `Function=4` => `MGATHER`
** `Function=5` => `MSCATTER`
** `Function=6` selects `MGATHER.MASK`.
** `Function=7` selects `MSCATTER.MASK`.
** `Function=8` selects `MGATHER.CAS`.
** `Function=9..12` select Shared `TMOV` modes.
** `Function=13` selects `GMOV`.
** `Function=14` selects Shared partition `TSTORE`.
** `Function=15..31` remain reserved/illegal unless a later manifest assigns them.
* `BSTART.TPREFETCH` is encoded as TLSU Function 3 with `mask=0x07ffffff` and `match=0x00311181`.
* `TPREFETCH` has the same address-generation, memory-fault, ordering, and restartability contract as `TLOAD`, with
  destination effects removed: no `B.IOT` destination binding, no tile allocation, no tile queue push, no tile metadata
  or data writeback, and no architectural destination dependency.
* `TPREFETCH` is not an optional hint. Implementations may choose the cache action, but they must perform the architectural
  checks and fault behavior required for the corresponding `TLOAD` footprint.
* Generic mixed TLSU textual forms remain illegal in canonical v0.58 sources. The legal public spelling is the assigned
  `BSTART.<alias>` form.
* The PTO map is frozen in `isa/v0.58/state/pto_encoding_map.json`: exactly 109 operations have one TLSU,
  CUBE, or TEPL disposition, and deleted or review-only names are rejected.
* CUBE Functions 1, 4-6, 16-18, and 20-22 have typed operation forms; every other unassigned function is illegal.

v0.58 block split patterns and per-family constraints:

* `BSTART.TLOAD` / `BSTART.TSTORE` (named TLSU Functions 0/1):
** use operation-applicable `B.DATR` layout/pad controls; inapplicable non-zero fields are illegal.
** accept zero or one `B.IOR`; omission selects base zero and dense row stride.
** bind `RegSrc0=base`, `RegSrc1=row_stride_elements`; a second B.IOR is illegal.
** require tile binding via `B.IOT`.
** are header-driven block commands (no SIMT body; do not use `B.TEXT`).
* `BSTART.TMATMUL`, `BSTART.TMATMUL.BIAS`, `BSTART.TMATMUL.ACC`, `BSTART.TMATMULMX*`,
  `BSTART.TGEMV*`, and `BSTART.TGEMVMX*` (assigned named CUBE-family functions):
** require `B.DIM`/`C.B.DIM*` with `LB0/LB1/LB2` bound as `m/n/k`.
** bind the exact source roles from `pto_ops.json` via `B.IOT` (left/right, plus bias or scale sources where applicable).
** bind one explicit destination through `destination0`.
** `.ACC` forms bind an explicit accumulator input through `source0`; non-`.ACC` forms have no accumulator input.
** when destination and accumulator name the same allocation, execution is read-old/write-new and requires identical
   data type, shape, layout, and allocation.
** no architectural implicit ACC singleton exists; `ACCCVT` is removed and reserved.
** are header-driven block commands (no SIMT body; do not use `B.TEXT`).
* `BSTART.VEC` / `BSTART.SFU` (TEPL carrier):
** operation is selected only by the raw `Mode` and `Function` fields.
** descriptor requirements are op-profile-specific, but tile and scalar bindings MUST still be expressed through block descriptors.
** PTO VEC/SFU forms (`TADD`, `TSUB`, `TROWMAX`, etc.) are header-driven in v0.58 (no SIMT body).
* `BSTART.VPAR` / `BSTART.VSEQ`:
** are the only TVEC-equivalent headers.
** require one `B.TEXT` target for the SIMT body in decoupled form.
** no `BSTART.TVEC` encoding exists in v0.58.

Future encoding-space growth policy:

* TLSU `Function` and CUBE `Function` expand by assigning new function codes; any new assignment MUST update:
** `isa/v0.58/opcodes/lx_32.opc`
** the alias table above
** strict profile checks and regression tests.
* The VEC/SFU TEPL carrier uses a two-bit Mode and five-bit Function selector. New assignments
  MUST be added to a later normative manifest and MUST NOT occupy a reserved
  pair implicitly.
* Future banks MUST be assigned explicitly by a later revision and carried by
  its machine-readable selector manifest.

[[blockisa-descriptors]]
=== Block header descriptors (B.* metadata)

In addition to a block start marker, a block may contain a short sequence of **block header descriptors** (`B.*`)
that define per-block metadata for accelerated/tile execution and for bring-up tooling.

Bring-up conventions:

* Block header descriptors are placed **immediately after** the block start marker.
* Block metadata is **reset at block start**. Descriptor repetition is legal only when the selected block schema permits
  it; PTO direct TileOp schemas permit at most one `B.IOR`, while Linx-only vector-body imports may use repeated `B.IOR`
  descriptors. Tooling should prefer *single assignment* where the schema permits it.
* Scalar-only implementations may treat most descriptors as **hints/no-ops**, but accelerated implementations may
  consult them for correctness (tile operand binding, ordering, traps).

The v0.58 catalog includes the following descriptor families:

* **Block I/O binding**
  - `B.IOR`: binds GPR inputs/outputs for a block.
  - `B.IOT`: binds Local tile inputs/outputs for a block (including last-use and transfer sizing).
  - `B.IOS`: binds an absolute Shared register, PE mask, and destination TSize.
* **Block arguments**
  - `B.DIM`: writes a block argument register (`LB0`–`LB2`) used for loop bounds, dimensions, and valid masks.
* **Block attributes and hints**
  - `B.CATR`: controls dependency, trap/far, atomic, acquire, and release behavior.
  - `B.DATR`: carries `CMode`, the PadValue/ByteId union, saturation, canonicalization,
    datatype, rounding mode, and layout. Every non-zero field must be applicable to the selected operation.
  - `B.HINT`: sets performance hints (branch likelihood, temperature, prefetch sizing, trace markers).
* **Text/offset annotations**
  - `B.TEXT`: in a decoupled block header, selects the out-of-line body entrypoint (`BodyTPC`). In coupled blocks it
    MAY be used as a tooling annotation.

NOTE: Detailed semantics for tile operand binding and for attribute/hint fields are under active bring-up. This manual
specifies the *encoded contract* (see <<insnref>>) and provides bring-up guidance; implementations may initially treat
these as metadata that does not affect scalar execution unless explicitly stated by the platform profile.

Strict runtime checks required by current bring-up profile:

* Tile descriptor size legality is fail-fast for both `B.IOT` and dynamic `B.IOT`.
* Tile-byte legality for tile blocks is fail-fast with the compiler/runtime formula:
  `tile_bytes = ceil(dim0 * dim1 * dim2 * element_bits / 8)` (`dim2=1` if absent for that block family).
  `element_bits` is derived from the v0.58 `DataType` mapping (including packed 4-bit formats).
* For SIMT-body blocks (`MPAR`/`MSEQ`/`VPAR`/`VSEQ`), descriptor legality is enforced at header ingestion:
  max 3 unique tile inputs and max 1 tile output descriptor binding.

[[blockisa-v058-ai]]
=== v0.58 AI extension rules

The canonical v0.58 profile integrates only reviewed and machine-readable
AI-oriented behavior:

* Canonical vector forms use `V.*`.
* Canonical block starts use only golden-catalog `BSTART.*` spellings.
* `B.IOT` group scheduling is defined for groups `0/1`; every other value is
  reserved/illegal.
* PTO operation names and selectors come only from
  `isa/v0.58/state/pto_encoding_map.json`.

[[blockisa-v058-pto-map]]
=== v0.58 canonical PTO-to-TAU mapping (auto-mode profile)

The canonical v0.58 auto-mode profile maps PTO tile primitives to typed TAU block headers and descriptors:

* `PTO TLOAD`:
  `BSTART.TLOAD` + `B.DIM(LB0/LB1/LB2)` + applicable `B.DATR` + `B.IOR*` + `B.IOT`
* `PTO TSTORE`:
  `BSTART.TSTORE` + `B.DIM(LB0/LB1/LB2)` + applicable `B.DATR` + `B.IOR*` + `B.IOT`
* `PTO TMOV`:
  `BSTART.TMOV` + applicable `B.DATR` + optional `B.DIM/B.IOR` + `B.IOT`
* `PTO TMATMUL`:
  `BSTART.TMATMUL` with explicit left/right sources and destination
* `PTO TMATMUL_ACC`:
  `BSTART.TMATMUL.ACC` with explicit accumulator/left/right sources and destination
* `PTO VEC/SFU ops` (`TADD`, `TSUB`, `TROWMAX`, ...):
  `BSTART.VEC TileOp, DataType` or `BSTART.SFU TileOp, DataType`; the assembler resolves
  `TileOp` to its assigned TEPL Mode/Function and emits the descriptor stream required by the operation contract.

Normative notes:

* `B.DATR + B.IOR` are required when their operation-specific contracts request datatype/layout/pad and scalar bindings.
* `TLOAD/TSTORE` dtype comes from encoded TLSU selector state (surfaced as `BSTART.TLOAD/BSTART.TSTORE` named forms),
  and applicable pad/layout policy comes from `B.DATR`.
* `TMOV` layout/convert policy comes from applicable `B.DATR` fields; destination tile kind/size comes from `B.IOT`.
* VEC/SFU operation selection is carried by the unchanged TEPL Mode/Function fields; no standalone `TVEC` header encoding exists.
* Multiple `B.IOR` and `B.IOT` descriptors in one header are legal and consumed in order.
* Every CUBE operation binds an explicit destination. `.ACC` forms additionally bind the accumulator source explicitly.
* Compiler strict checks MUST reject a `.ACC` form with a missing accumulator source or an incompatible
  destination/accumulator alias. Same-allocation aliases read the old accumulator value before writing the new result.
* Canonical v0.58 artifacts MUST NOT encode reserved `group=2` behavior.

[[blockisa-simt]]
=== SIMT-style vector blocks (`MSEQ`/`MPAR`/`VSEQ`/`VPAR`)

Linx vector execution is SIMT-style: a vector block body is a **group-granular kernel body** executed across the lane/group
space defined by `LB0..LB2`.

`TVEC` is not a v0.58 header mnemonic. TVEC-style execution is represented by `BSTART.VPAR`/`BSTART.VSEQ` with
an out-of-line SIMT body selected by `B.TEXT`.

Execution model (normative for v0.58):

* `LB0..LB2` are written by `B.DIM` / `C.B.DIM*` in the block header.
* Hardware exposes lane/group counters `lc0..lc2` to the block body.
* For the canonical 1-D kernel profile:
** `lc0` is the lane index within a group,
** `lc1` is the group index,
** `lc2` is `0` unless a higher-dimensional profile is selected.
* Each group instance enters the body once with:
** one architectural group PC,
** one architectural EXEC mask `p`,
** `LB0` lanes available in the group.
* `MSEQ` / `VSEQ`: group-visible effects are committed in lexicographic group order.
* `MPAR` / `VPAR`: groups are conceptually parallel; an implementation MAY commit groups in any order, but MUST be
  observationally equivalent to some interleaving consistent with the architectural memory-order rules.
* Group interpretation for canonical 1-D lowering:
** `LB0` denotes lanes per group (`lane_count`),
** `LB1` denotes group count (`group_count`),
** the linear lane index is `lc0 + lc1 * lane_count`.
* Scalar instructions in vector bodies are **uniform per group** (one scalar-uniform control step per group PC step).
* Vector instructions execute across the currently active lanes selected by `p`.
* Divergent control flow is represented by explicit updates to `p` inside the body; canonical `v0.58` does not require a hidden
  per-lane architectural PC.

Decoupled body form (v0.58 canonical constraint):

* The header MUST contain exactly one `B.TEXT <tpc>` selecting an out-of-line body.
* The body MUST terminate at a block terminator marker. Valid terminators are `BSTOP` / `C.BSTOP` and `BSTART.*` / `C.BSTART.*`.
  - First terminator wins (anything after is unreachable).
  - Any `BSTART` encountered inside the body stream acts as both the terminator trigger and the next architectural block start
    after the kernel returns to the header continuation point.
* The body MUST NOT contain any `B.*` header descriptors.
* For canonical `MPAR` / `MSEQ` shader kernels, the body is a structured instruction stream; in-body branches and jumps are legal,
  control flow is group-internal, and `p` is the architectural EXEC mask.
* In-body control transfers MUST remain within the current body region selected by `B.TEXT`.
* Divergent regions are represented by explicit management of `p`; join points are explicit points in the body stream where the
  intended EXEC mask is restored.

Example (2-D nested loop using `MSEQ`):

[source,asm]
----
    # for (i=0; i<n; i++)
    #   for (j=0; j<m; j++)
    #     a[i][j] = i + j

	    BSTART.MSEQ 0
	    B.TEXT .body
	    B.IOR [s0],[]          # a base pointer mapped to ri0
	    B.DIM a0, 0, ->lb0     # m
	    B.DIM a1, 0, ->lb1     # n
	    C.BSTART

.body:
	    v.add lc0, lc1.sw, ->vt
	    v.sw.brg vt#1, [ri0, lc0<<2, lc1<<10]   # example stride: 1024B = (1<<10)
	    C.BSTOP
----

[[blockisa-rdc]]
=== Vector reduction operations in SIMT bodies (`V.RD*`)

`V.RD*` operations provide lane-to-scalar reductions inside vector bodies:

* `V.RDADD`, `V.RDAND`, `V.RDOR`, `V.RDXOR`, `V.RDMIN`, `V.RDMAX`,
  `V.RDFADD`, `V.RDFMIN`, `V.RDFMAX`.
* Source operand is a vector-lane value (`vt`/`vu`/`vm`/`vn` namespace).
* Destination is a scalar destination encoding:
** block/group-local scalar state (`t/u` and profile-defined block-local scalar destinations), or
** global scalar registers (`R0..R23`) for inter-group accumulation.

Execution/ordering rules:

* `MSEQ` reductions are deterministic in lexical `LC` replay order.
* `MPAR` reductions are only valid when dependence-safe; compiler emission must require associative/commutative legality
  (or an explicit programmer parallel hint with matching semantics).
* Non-associative reductions in `MPAR` are illegal unless the profile explicitly defines the numerical relaxation.
* Strict bring-up compiler lowering of reduction live-outs MAY stage through a bridged scratch path:
  `V.RD*` to scalar destination, followed by `V.SW.BRG` to an `ri*`-bound scratch slot consumed by scalar continuation code.
* The lowering form requires an operation-identity initializer (`0` for add/xor/or, `-1` for and, `1` for mul when enabled).

[[blockisa-v04-bridge]]
=== Kernel memory-bridge naming (canonical profile)

For canonical shader kernels, bridge operands and mnemonic families are:

* `load.local` / `store.local`: tile/local direction accesses.
* `load.brg` / `store.brg`: bridged global-memory accesses.
* `ri0..ri11`: ordered scalar-import namespace mapped from `B.IOR`.
* `TA`, `TB`: vector input tile bases.
* `TO`: vector output tile base.
* `TS`: vector scratch tile base.
* Archived raw names `TE..TH` and `TO1/TO2/TO3` are not part of canonical v0.58 and remain reserved/unassigned.

Encoding/mnemonic mapping (normative):

* `load.local` / `store.local` correspond to tile-local access forms.
* `load.brg` / `store.brg` correspond to bridged global-memory access forms.
* In the unified `lx64` kernel space, both scalar-uniform `l.*` forms and per-lane `v.*` forms may use `.brg`.

Bring-up operand constraints (strict profile):

* `.brg` kernel memory ops MUST use `ri*` as their base operand (`SrcL`); using arbitrary scalar GPR names directly is illegal.
* `.local` vector memory ops MUST use tile bases (`TA/TB/TC/TD/TO/TS`) as their base operand (`SrcL`).
* `.local` accesses MUST remain within the tracked byte-size of the referenced bound tile; out-of-range tile-local access is illegal.
* `.local` stores MUST target output/scratch bases only (`TO` or `TS`). `TA/TB/TC/TD` are read-only input bases in
  canonical v0.58.
* `VSEQ`/`VPAR` remain tile-only vector execution forms; canonical shader-kernel global-memory issue uses `MPAR`/`MSEQ`.

Bring-up tile-base binding for `.local` ops (normative for v0.58):

* Tile bases are derived from the header's `B.IOT` descriptors in header order:
** `TA/TB/TC/TD` map to the first four *present* source tiles across the descriptor stream (in `SrcTile0` then
   `SrcTile1` order).
** `TO/TS` map to the first two destination tiles encoded in an *absent* source slot (preferring `SrcTile1`, then
   `SrcTile0`), matching the canonical disassembly contract for `B.IOT`.
** Archived raw names `TE..TH` and `TO1/TO2/TO3` are not assigned by the canonical binding algorithm.
* If a referenced base is not bound by the current header, the access is illegal.

Vector block bodies may mix scalar-uniform and vector instructions; scalar-uniform forms use scalar block-local state
(`GPR`, `t/u`, block-condition state), while vector forms use vector/tile-local namespaces.

Predicate and divergence semantics for mixed bodies:

* `SETC.*` in the body updates the scalar block-control predicate domain (`BARG.CARG`); it does not directly mask vector lanes.
* `p` is the architectural EXEC mask for canonical `MPAR` / `MSEQ` kernels, and `V.CMP.* ->p` is the normative mask producer.
* Scalar instructions execute once per group control-flow step in program order together with vector instructions.
* Vector instructions execute for the currently active lanes selected by `p`.
* Divergent control flow narrows, restores, or otherwise updates `p` under the current group PC; canonical `v0.58` does not rely on
  a hidden architectural lane-PC stack.
* Vector instructions MUST import scalar inputs through `B.IOR`/`ri*` (except `zero` where encoding permits). Direct scalar
  GPR operand names in `V.*` forms are illegal in canonical kernel bodies.

[[blockisa-bcmd]]
=== Block-command lifecycle

The architectural interface between the first and second layer is a block command:

* `BSTART.<type>` begins a new command:
** packs the block opcode/type (and any type-specific info) into the command header.
** conceptually allocates a `BID` (block ID) for `BROB` tracking.
* Header descriptors pack additional command fields:
** `B.IOR`: reads input GPR values when they are ready and packs them into the command payload; reserves tags for GPR
   live-outs.
** `B.IOT`: performs tile rename, computes input/output tile base addresses, and packs those addresses into the command
   payload.
** `B.CATR/B.DATR`: pack block-type-defined control and data attributes.
** `B.DIM`: packs block dimensions (`LB0..LB2`) for SIMT/vector replay and for tile engines.
** `B.TEXT`: packs the out-of-line body `TPC` for decoupled blocks.
* `BSTOP` (or an implicit boundary at the next block start marker) finalizes the command and dispatches it to the
  selected second-layer PE.
* The PE executes only when a valid command is received; it may buffer multiple commands internally.
* On completion (or fault), the PE returns:
** live-out values (GPR writes and/or tile writes) for architectural state update, and
** a status code (success, fail, exception metadata) for `BROB`.
* `BROB` tracks completion and retires block commands in-order; speculative commands may be flushed by misprediction.

[[blockisa-tepl]]
=== VEC/SFU Tile engines (TEPL carrier)

`BSTART.VEC TileOp, DataType` and `BSTART.SFU TileOp, DataType` select catalogued
VEC and SFU operations through the unchanged TEPL Mode/Function encoding.
`BSTART.TEPL Mode, Function, DataType` is an accepted
compatibility spelling for the same carrier; it is not a fifth engine or an
extension namespace.

* VEC/SFU headers use the same descriptor families (`B.CATR/B.DATR`, `B.IOR`, `B.IOT`) as other decoupled blocks.
* `Mode` and `Function` select only operations assigned by the v0.58 catalog; `DataType` is carried in the same header.
* VEC/SFU operations are header-driven and do not require a separate SIMT body selector.
* Unassigned Mode/Function pairs are illegal and MUST NOT acquire implementation-defined semantics.
* VEC/SFU blocks must follow the same block-boundary legality rules and must not directly bypass the memory and
  privilege contracts defined in this manual.

[[blockisa-assembly]]
=== Assembly/disassembly conventions

* The default block type `.STD` is omitted:
  - `BSTART` means `BSTART.STD`
  - `C.BSTART` means `C.BSTART.STD`
* For returns, a common convention is:
  - `C.BSTART RET` then `c.setc.tgt ra`

`SETC.TGT` selects a register or link target used by `RET`/`IND`-class transitions in the common convention above.
`SETRET`/`C.SETRET` materialize a return address into `ra` for call sequences.

NOTE: The bring-up profile notes that `C.BSTOP` is encoded as all-zeros in the 16-bit space; it functions both as an
invalid/reserved encoding and as the block-stop marker in current conventions.

[[blockisa-call-return]]
=== Calls, returns, and return addresses

In the current toolchain bring-up:

* Calls are represented as a block transition (`BSTART.STD CALL, <target>`).
* Generic bare calls use `BSTART.STD CALL, <target>` and preserve `ra`.
* The exact 32-bit `BSTART.CALL <br_label>, <rt_label>, ->ra` and 48-bit
  `HL.BSTART.CALL <br_label>, <rt_label>, ->ra` forms are fused returning calls. They encode both labels and write
  `ra`; they are not bare-call aliases.
* Other returning-call sequences materialize the explicit return label in `ra` using an adjacent `SETRET` or
  `C.SETRET`.
* `FRET.STK` is treated as a `ret`-class encoding extension by some tooling (e.g. callgraph analysis).

**Exact fused-call contract:**

Let `P` be the address of the first byte of the aggregate form. The two encoded immediates are independent
PC-relative operands even though their bit ranges are adjacent:

* 32-bit exact form (`bstart_call_32_9404418d1ae5`):
** `call_target = P + (SignExtend(simm12) << 1)`
** `ra = (P + 2) + (ZeroExtend(uimm5) << 1)`
** relocations: `CBSTART12_PCREL` and `CSETRET5_PCREL`
* 48-bit exact form (`hl_bstart_call_48_3c784c583c90`):
** `call_target = P + (SignExtend(simm25) << 1)`
** `ra = (P + 4) + (ZeroExtend(uimm5) << 1)`
** relocations: `B25_PCREL` and `CSETRET5_PCREL`

Both offsets use halfword units. The return delta is unsigned and therefore spans 0 through 62 bytes from the
embedded `C.SETRET` base. Assemblers and linkers MUST reject odd deltas, signed branch overflow, negative return
deltas, and return deltas greater than 62 bytes rather than truncate them. The decoded aggregate performs the CALL
transfer and `ra` write atomically. Changing `simm12`/`simm25` MUST NOT change `ra`; changing `uimm5` MUST NOT change
`call_target`. Concatenating the adjacent fields into one logical target is non-conforming.

**Constraint (call header pairing):**

When a standalone `SETRET`/`C.SETRET` is used to materialize the return address for a generic call transition, it must
appear **immediately before** the call-type block start marker (e.g. `BSTART.STD CALL, <target>` / `C.BSTART CALL`).
Tooling and hardware may fuse that instruction pair; no other instruction may be placed between them. This source
pair is distinct from the exact aggregate `BSTART.CALL`/`HL.BSTART.CALL` forms above, whose embedded `C.SETRET` field
is already part of the same encoded instruction.

[[blockisa-examples]]
=== Example patterns

The following snippets are representative patterns; exact scheduling and block splitting are toolchain-dependent.

*Conditional block transition:*

[source,asm]
----
setc.ne  a0, zero
BSTART   COND, label
----

In this pattern, `SETC.*` produces a block-local condition that is consumed by `BSTART COND`. A typical interpretation
is:

* if the condition is true: branch to `label`
* otherwise: fall through to the next sequential block in the instruction stream

NOTE: With the safety rule above, `label` must refer to a block start marker (e.g. `BSTART.*` or a template block such
as `FENTRY`/`FRET.*`). Branching into the interior of another block is invalid and raises an exception.

*Direct call with explicit return address:*

[source,asm]
----
BSTART.STD    CALL, callee, ra=return_label
----

*Exact aggregate call with two explicit targets:*

[source,asm]
----
BSTART.CALL   callee, return_label, ->ra
----
